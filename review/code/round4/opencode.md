### [HIGH] Reused row ids let a stale editor overwrite a different expense
`src/index.ts:640-656` (schema `migrations/0001_init.sql:35`). Scenario: the newest expense is deleted and a replacement is added, so SQLite reuses the deleted `INTEGER PRIMARY KEY`; a parent still has the deleted expense open and taps Save or Delete. The server re-reads the reused id as `old` and only checks that the trip is open, so it writes the stale body or deletes the replacement. Wrong outcome: an unrelated expense is silently replaced or deleted, its receipt is swapped/dropped, and balances change; families and people have the same id-reuse exposure. Suggested fix: use `AUTOINCREMENT` ids or send a per-row `created_at`/`updated_at` token from the editor and require it in the PATCH/DELETE `WHERE`.

### [MEDIUM] Family-screen redraw restores stale text and Fencer state captured before the reload
`public/app.js:710-719`. Scenario: a day/fencer save is in flight; while its follow-up `loadTrip` runs, the parent types the next child’s name, edits pay notes, or ticks/unt ticks Fencer. `famSave` captured `typed` and `fencerTicked` before the `await` at line 714, then writes those older values back after `renderFamily` at 717-719. Wrong outcome: text entered during the reload is reverted, and a Fencer change made in that window is undone; tapping Add can save the child with the wrong `is_fencer`, changing coach-travel/stay shares. Suggested fix: take the capture after `await loadTrip` and immediately before `renderFamily`, including the checkbox’s then-current state.

### [MEDIUM] An action response arriving after navigation reopens the old trip over the new screen
`public/app.js:227-230` (for example `:1272`). Scenario: tick a payment or finalize, then immediately press Back or open another trip while the request is slow. The response calls `refresh` after navigation, so the `routeSeq` captured inside `refresh` is the new route’s and passes; `loadTrip(S.trip.tournament.id)` then reloads the old trip and `renderTrip` paints it over the new screen. Wrong outcome: the URL and the screen/`S.trip` disagree, and the next action edits or ticks the painted trip rather than the one in the URL. Suggested fix: capture the trip id and `routeSeq` when the action starts, and skip the refresh/assignment if the hash no longer points at that trip; do not mutate `S.trip` until after the check.

### [MEDIUM] A hand-set split is discarded or reinterpreted when the split basis changes
`public/app.js:851, 918, 929, 1002-1005`. Scenario: on a new expense, hand-set a family’s units or untick one (`splitTouched` true, `basisTouched` still false). A manual Category change to a different-basis category calls `resetSplit()` and discards it; if the same category comes from a receipt instead, `fillFromReceipt` changes the basis but keeps the split, so the numbers now mean a different unit. Wrong outcome: a deliberate count/exclusion is silently dropped, or the old number is reinterpreted as fencer-days instead of people, changing shares and balances. Suggested fix: mark `basisTouched` when the split is hand-edited so the basis stays under the numbers, or reset the split consistently in both paths whenever the basis changes.

### [LOW] `here()` prefix match treats family 1 and family 12 as the same screen
`public/app.js:704`. Scenario: a save from family 1 is still queued when the user opens family 12; `startsWith("#/t/1/f/1")` is true for `#/t/1/f/12`, so the redraw renders family 1 while the URL is family 12. A tap on that redrawn screen queues changes for family 1, and its later redraw repeats the match. Wrong outcome: days or people are edited on the wrong family. Suggested fix: parse the path and compare the numeric family id, or require the prefix to end at `?` or end-of-string.

### [LOW] A failed Add can restore the name and tick into a different family’s form
`public/app.js:763-766`. Scenario: the person POST fails slowly; the parent navigates to another family and starts typing a new name/tick; the awaited `famSave` returns and the failure branch writes `n`/`fencer` into whatever `#newname`/`#newfencer` is now on screen. Wrong outcome: the new form’s typed text is replaced and the next Add can save the wrong name/fencer. Suggested fix: verify the hash still matches this family before restoring, or capture a screen token and compare it.

### [LOW] Family search does not hide non-matching rows
`public/app.js:556`; `public/styles.css:419`. Scenario: with more than eight families, type a search; `a.hidden = true` is overridden by the author rule `.famrow { display: flex }`, so every row stays visible while the “No family or person matches that” message can also appear. Wrong outcome: the search looks broken and the list is not filtered. Suggested fix: add `#famlist .famrow[hidden] { display: none }` or toggle an inline display/class instead of `hidden`.
