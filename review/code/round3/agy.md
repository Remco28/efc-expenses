### [HIGH] New person's fencer status is silently lost on family screen redraw
public/app.js:701. Scenario: On a family's screen (`renderFamily`), a parent enters a name in `#newname` ("Sophia") and checks the "Fencer" switch (`#newfencer.checked = true`). Before clicking "Add", the parent taps a day button for another person (or an in-flight save from an earlier tap completes). `famSave` runs and redraws the screen. While `keepIds` preserves text inputs, it omits `#newfencer` (and checkboxes store `.checked`, not `.value`). The redraw recreates `<form id="addperson">` with `#newfencer` unchecked. The parent taps "Add". Wrong outcome: The child is saved to the database with `is_fencer = 0` and `fencing_days = []`. Sophia is silently excluded from all per-fencer (coach travel, supplies) and per-fencer-day (coach stay) cost splits without anyone noticing. Suggested fix: In `famSave`, capture `document.getElementById("newfencer")?.checked` before the redraw and restore it to `document.getElementById("newfencer").checked` afterward.

### [HIGH] Redraw value restoration clears browser dirty flag, dropping edits on blur
public/app.js:708-709. Scenario: A parent opens their family screen, focuses `#fam-pay` (payment notes), and types "Zelle 555-0123". While typing, a background save from an earlier day tap finishes. `famSave` captures the typed string and, after calling `renderFamily`, programmatically sets `el.value = v`. Under the HTML specification, setting `.value` programmatically clears the element's user-modified dirty flag. When the parent stops typing and clicks "Done" (`<a ...>Done</a>`), the input blurs. Because the dirty flag is false, the browser does not dispatch a `change` event. Wrong outcome: `pay.onchange` never fires. The payment notes (or edited family/person name) are never sent to the server and are silently discarded when leaving the screen. Suggested fix: After setting `el.value = v` (or `el.value = typedName[1]`), update `el.defaultValue = v`, or dispatch `el.dispatchEvent(new Event("change"))` if `el.value !== el.defaultValue`.

### [HIGH] Changing category on an existing expense fails to update its split basis
public/app.js:798, 837. Scenario: An expense was previously saved under "Team meal" (default basis: `person`, headcount split). A parent reopens the expense to correct it to "Ground transport" (`transport`, default basis: `family`). When opening an existing expense, line 798 unconditionally sets `basisTouched: true`. When the parent picks Ground transport in the category dropdown, `cat.onchange` checks `if (!d.basisTouched)` before setting `d.basis = CATEGORIES[d.category].basis` and calling `resetSplit()`. Because `basisTouched` is already true, `d.basis` remains `"person"`. The parent saves the changes. Wrong outcome: The van rental continues to be split per person by headcount instead of per family. A family with 4 people is charged 4x as much as a family with 1 person. Suggested fix: In `renderEditor`, do not initialize `basisTouched: true` if `e.basis === CATEGORIES[e.category]?.basis`, or reset `basisTouched` when the category dropdown changes.

### [HIGH] Tournament finalize fingerprint omits `treasurer_family_id`
src/index.ts:120-123, 402. Scenario: Tournament 1 has treasurer Lisa Chen (`treasurer_family_id = 1`). User A clicks "Finalize trip", which fetches `loadTrip` and computes `plan = treasurerPlan(rows, 1)` (omitting Family 1 from payments). Concurrently, Mark Davis volunteers as treasurer, sending `PUT /tournaments/1/treasurer` (`treasurer_family_id = 2`). Because `FINGERPRINT_SQL` only selects from `expenses`, `people`, and `families`, it does not check `tournaments.treasurer_family_id`. The fingerprint matches, and the atomic finalize batch commits. Wrong outcome: Finalized payments omit Family 1 (who was not the treasurer when finalized) and charge Family 2 (who is the final treasurer and now owes/receives money to/from themselves). Suggested fix: Add `|| '#' || (SELECT COALESCE(treasurer_family_id, 0) FROM tournaments WHERE id = ?)` to `FINGERPRINT_SQL`.

### [MEDIUM] `famSave` displays success checkmark ("✓ Saved") when a save fails
public/app.js:691, 710. Scenario: A parent taps a day button or toggles a fencer on the family screen. The network drops or the server rejects the mutation (e.g. 409 conflict). `act(call)` throws an error and displays an error toast. However, `famQueue = famQueue.then(() => act(call)).catch(() => {}).then(...)` catches and swallows the rejection, proceeding to the final `.then` block which executes `st().textContent = '✓ ${msg}'`. Wrong outcome: The screen displays a green "✓ Saved" checkmark in the header, falsely assuring the parent their edit landed when it was actually rejected. Suggested fix: Track whether `act(call)` succeeded and only display `✓ ${msg}` if no error occurred.

### [MEDIUM] Pruning trip dates skips attendance of members with concurrent edits
src/index.ts:371-374. Scenario: A trip running Friday through Sunday is shortened to Saturday. Concurrently, a parent toggles Friday attendance for their child. The child's `people` row is updated with Friday added. When the organizer's batch executes `UPDATE people SET days = ?, fencing_days = ? WHERE ... AND days = ? AND fencing_days = ?`, the `AND days = ?` condition fails because Friday was added. The update skips the row. Wrong outcome: The child retains Sunday in `people.days` and `people.fencing_days`. Because Sunday is outside the tournament dates, it is invisible in the UI and cannot be unticked, but `split.js` continues to count the dropped Sunday in per-fencer-day expenses. Suggested fix: Clamp `days` and `fencing_days` with an unconditional update rather than skipping the row when `days` changed.
