### [MEDIUM] Redraw can leave restored payment details unsaved
[public/app.js:719](/home/frank/Dev/efc-expenses/public/app.js:719). Scenario: Remove a person, then type new payment details while that save/reload is pending. The redraw restores the text but applies `focusAfter = "#newname"`. Wrong outcome: The restored payment input is unfocused and never fires its blur-based `change` handler. Tapping Done silently discards the displayed edit. Suggested fix: Preserve the currently edited input’s focus instead of applying `focusAfter`, or explicitly save dirty values when moving focus.

### [MEDIUM] Reverting a field during reload silently restores the unwanted value
[public/app.js:721](/home/frank/Dev/efc-expenses/public/app.js:721). Scenario: Payment details initially contain A. Change them to B and blur to save. While the follow-up GET is pending, focus the field and change it back to A. Wrong outcome: Because A equals the old element’s `defaultValue`, the preservation filter excludes it; the redraw replaces it with saved B, losing the correction. Family, staff and person names have the same exposure. Suggested fix: Track edits since the submitted save rather than comparing against the original DOM default.

### [MEDIUM] Expense identity protection still races with deletion and ID reuse
[src/index.ts:655](/home/frank/Dev/efc-expenses/src/index.ts:655). Scenario: A PATCH reads an expense and passes the new `created_at` check. While its asynchronous validation runs, another parent deletes that newest expense and adds a replacement that reuses its ID. Wrong outcome: The UPDATE matches only the ID and open-trip condition, silently overwriting the replacement. DELETE has the same gap. Suggested fix: Include the expected `created_at` and tournament ID in both mutation predicates, and reject when no row matches.
