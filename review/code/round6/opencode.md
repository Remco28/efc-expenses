### [MEDIUM] A stale save can resurrect a receipt that was already deleted
File: src/index.ts:652-658 (with dropReceipt at 62-66). Scenario: Expense E has receipt A. Two parents open E's editor. Parent 1 uploads receipt B and saves, so the row becomes B and `dropReceipt` deletes A from R2. Parent 2 then saves an unrelated edit (say the amount) from the still-open editor whose draft still names receipt A. The UPDATE writes A back; because `old.receipt_key` is now B, `dropReceipt` deletes B. Wrong outcome: E points at A, which no longer exists (broken receipt; "View receipt" 404s), and the newer B has been deleted too. Suggested fix: verify the submitted `receipt_key` still exists in R2 before accepting it (reject 409 if not), or include the expected old `receipt_key` in the UPDATE predicate so the stale save fails.

### [LOW] The created_at identity check is optional
File: src/index.ts:649-650, 655, 663. Scenario: The newest expense (id 55, created_at T) is deleted and a replacement gets the reused id 55 with created_at T'. A request that omits `created_at` (an old cached client, or simply `DELETE /api/expenses/55` with no body) skips the check; `old` is then the replacement row, so its own timestamp is used in the WHERE and the request succeeds. Wrong outcome: the unrelated replacement expense is silently deleted, or overwritten by a PATCH, even though sending the old T would have produced a 409. Suggested fix: require `created_at` on PATCH and DELETE and use the client-supplied value in the WHERE (plus `tournament_id`); reject requests that omit it.

### [LOW] Non-canonical split keys pass validation but are ignored by the split math
File: src/index.ts:198-203. Scenario: A client sends `split: {"01": 5}` (or `" 1"`, `"1.0"`) for family 1. `ids.has(Number(k))` accepts it and the value is stored under the literal key `"01"`. `split.js` looks up `String(f.id)`, i.e. `"1"`, so the override is not found. Wrong outcome: family 1 is treated as automatic (or 0 for a custom split) instead of the submitted count/share; the expense is silently split differently from what was saved, and can even become unsplit. Suggested fix: canonicalize the key (`const id = Number(k); split[String(id)] = ...`) or reject keys that are not exactly `String(Number(k))`.
