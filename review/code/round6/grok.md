### [MEDIUM] Redraw re-saves a field the server just normalized, forever
File: `public/app.js:733`. Scenario: On a family or coach screen, set the family name, payment notes, or role to a value the server will not store as typed, then leave the field. The server trims ends and cuts notes at 300 characters, names at 200, and roles at 40 (`src/index.ts:60`, family update around line 521). A trailing space from the phone keyboard is enough; so is a role such as "Assistant coach and armorer for this trip". The save succeeds, the reload draws the shortened value, and the new code puts the original text back and fires `change` because it differs. Wrong outcome: That `change` saves again, the reload differs again, and the screen loops saves for as long as it stays open, flashing "✓ Saved" while still showing the untrimmed or uncut text. A note longer than the cap looks saved in full but is stored cut off. Any edit another parent makes to that same field is written back over on the next loop. Suggested fix: Do not fire `change` from the reload. Remember the text last submitted, and send it again only if it differs from that and from what the server returned.

### [MEDIUM] A successful refresh is dropped when the phone is backgrounded
File: `public/app.js:231`. Scenario: Tick a payment, save trip details, or finalize, so `refresh()` is in flight. Switch to another app (Venmo, Messages) and come back before that request returns. Coming back runs `route()`, which bumps `routeSeq`, even though the hash is still this trip. `refresh()` now requires the same `routeSeq`, so it throws away the trip it just loaded. Wrong outcome: If the visibility reload then fails on a bad connection, the catch paints "Couldn't load this page" and nothing applies the refresh that succeeded. The save did stick; the checklist or the saved details are gone until the trip is opened again. Previously a refresh still drew while the URL stayed on this trip. Suggested fix: Skip `renderTrip` only when the trip path or the tab query changed. A visibility reload of the same URL should not discard a refresh that already succeeded.
