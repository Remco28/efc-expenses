Review of the retry-key plan, checked against /home/frank/Dev/efc-expenses (read only; nothing run or changed). Short verdict: the core holds up (server-side idempotency per key, phone writes the key before sending and keeps it until a real answer, a separate slot per kind). It is not ready to build as written. Several items below are existing bugs or places where the plan's own rules would reintroduce them.

WHAT THE PLAN BREAKS THAT WORKS TODAY
1. Corrected expense retries. Today POST /tournaments/:id/expenses with a known key applies the correction if the row is untouched (UPDATE ... rev = 0, src/index.ts around line 722-735). Plan item 1 removes this. Plan item 5 only covers "did save" on the trip screen or Add expense, not a corrected retry. The path that matters: a save gets no reply, the form stays open (saveExpense in public/app.js keeps S.draft), the parent fixes the amount and taps Save again. Same key, corrected amount: the server returns the original row unchanged, the app says "Expense saved" and closes. The wrong amount is saved and the parent has no reason to look. The R9 round fixed exactly this, and the plan reverses it without saying so.
2. Typo fixes for people, families and trips. Migration 0011 and commit 2615cfc made the untouched first row take the corrected name. The plan replaces that with "Av was added after all", which is a defensible choice, but it is a reversal of a recent deliberate decision and the plan should say so and say why. The cost is that the most common case (a typo) now takes an extra step.

WHERE THE "KEY STAYS" RULE IS NOT WHAT THE CODE DOES
3. Stalled replies. api() in public/app.js clears its timeout as soon as headers arrive (the finally around line 93), so res.json() can hang forever. The family screen queues every save (famQueue, around lines 747-790), so one hung add freezes all saves on that screen and the Add button never re-enables. The plan says a stalled reply counts as "don't know", but the code does not implement that.
4. The key is forgotten too early. forgetAddKey runs (line 95) before res.json(), and for every response, including a 502 HTML page from the network. A half-received reply or an error page therefore drops the key, the opposite of plan item 2.
5. 10-minute expiry. ADD_TTL (about line 60) expires keys after 10 minutes, and the storage is sessionStorage (gone when the tab closes). Plan item 2 requires keys to survive closing the app and to last until a real answer. The TTL must go, or a retry after 10 minutes gets a new key and adds a duplicate.
6. Expense pending is written only after a failed request (keepPending in saveExpense's catch). A stalled body, or the app being killed while the request is in flight, leaves nothing on disk. Plan item 5 needs write-before-send.
7. 5xx is ambiguous. The Worker's own "Something went wrong" 500 can follow a committed row, because the activity log insert is a separate statement after the row insert. If the phone treats any readable reply as a real answer (plan item 2), it forgets the key and the retry adds a duplicate. Rule to write down: only 2xx and 4xx JSON from the app are answers; any 5xx, and any non-app page, is "don't know".
8. Concurrency. Expense inserts use ON CONFLICT DO NOTHING. People, families and trips inserts do not, so a concurrent same-key second request throws a UNIQUE error and returns 500. Plan item 1's "can't crash" needs the same handling everywhere (or a claim row written in the same D1 batch).

KEY COLLISIONS (the slot design is right in principle but under-specified)
9. Keys are per path today (addKeyFor(path)). Persons are keyed per family, so a lost-reply "Rosa" followed by a new "Mia" in the same family sends Rosa's key with Mia's name. The server answers "Rosa" and the phone says "Rosa was added after all. Fix the name in the list". A parent who follows that renames Rosa to Mia. A key has to be bound to one intended add. A new intent gets a new key, and the old pending add stays in its own record until it is checked.
10. Families and coaches share the same path (/tournaments/:id/families), so they share a slot today. Reproduced by reading: a lost family add, then a coach add in the same tab, reuses the key. The server's update changes the family's role and never changes its kind, so the coach ends up as a family row. The per-kind slot fixes this only if the server also refuses a key whose stored kind differs. The plan does not say that.
11. Trips use one global slot. A second trip added within the window gets the first trip's key and is flagged or renamed.
12. "One per trip" for expenses. keepPending is a single global record that the next failure overwrites. Two lost replies in a row lose the first one, which may have landed, and the parent may re-add it. Either keep a list or block a new add while one is unchecked. Blocking is simpler to explain.
13. Re-entering from scratch. The check runs only when the parent returns to the trip screen or Add expense. A parent who re-enters right away creates a second expense. Later the first is marked "did save", the pending record is cleared, and the duplicate stays. The check has to run before a new add of that kind is allowed.

TOMBSTONES ARE ONLY PLANNED FOR EXPENSES
14. People and families can be deleted (DELETE routes) and trips are soft-deleted and purged after 30 days (purgeTrip). Today a retry for a deleted person or family re-inserts it, because nothing remembers the key. A soft-deleted trip returns its id with 200, and the phone then opens a 404. After purge, a retry creates a new trip. The fix is one key registry table (key, kind, tournament, row id, deleted_at) covering all four kinds, with a stated retention rule for purged trips. That needs a new migration, which the plan does not mention. The same registry replaces the client_key columns, partial unique indexes and client_sig columns, which is simpler.

CONTRACT AND MESSAGES
15. Add responses today are {id} only. Plan item 3 needs the stored details and a comparison. Do not compare on the phone: trimming, the 300-character cap, default role "Coach", people's days copied from the family at insert time, and expense normalization would all show false "added after all" warnings on identical retries. Have the server compute a boolean "same" with the same normalization it uses for storage, and return the stored values.
16. The expense "did save" and "Expense saved" messages need the same "differs" check as the people messages. Right now they do not.
17. Receipts. A pending expense holds a receipt key. If the retry happens after the upload is gone, the server answers "receipt upload has expired" (a 409, so refused), the phone forgets the key, and the expense is lost with an error. The plan does not say what the pending record keeps, or what happens to it.
18. Storage survival. "Survives closing the app" should be checked on the real phones (iOS home-screen web apps especially) rather than assumed.

IS IT TOO COMPLICATED?
Yes, a little. The plan has per-kind reload checks, an expense-only settle path, expense-only tombstones and per-kind slots. A simpler shape: one pending-add record type (kind, scope, key, typed values, created time) in localStorage, written before the request and removed only on a real answer. One resolve step checks the loaded trip for the key; the trip payload already includes client_key on people, families and expenses (SELECT *). One server registry for keys. Drop client_sig, the TTL and sessionStorage. Block a new add of a kind while one is pending. The server returns {id, same, stored}.

TESTS
There are no server tests (test/ covers only the split math). Build the core test first: commit a write, drop the response, retry. Then cover concurrent same-key, delete-then-retry, purge-then-retry, and kind mismatch.

WHAT HOLDS UP
Server-side idempotency per key with unique indexes; the expense path is already close to the plan; write-before-send with a stable key; keeping the key on no answer; separate kinds for the coach/family collision; deleting the client_sig logic makes the server simpler.
