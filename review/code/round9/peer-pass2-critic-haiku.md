Verdict: the plain retry works (same details after a lost reply, same key, comes back 200 and nothing is doubled), and the expense dedupe holds for the common case. The part that does not hold up is the "corrected retry" rule, and the cause is the key's scope, not the server check. Read-only review; I ran nothing and changed nothing. Line numbers are from the current tree (efc-expenses, HEAD 2615cfc).

**Most likely to hurt a parent (no reload or bad signal needed)**

1. The key is per path per tab, not per add. `api()` (public/app.js ~84-85) keys on the URL, and the key is only dropped when an answer arrives. Two different adds of the same kind within 10 minutes of a lost reply therefore share a key, and the server treats the second as a correction of the first:
   - Trip: lost reply on "Summer Nationals", then New trip "Fall Classic" within 10 minutes (no families yet). The server renames the first trip to Fall Classic and moves its dates. Trip creation does not reload, so nothing warns the parent. Toast: "Trip created".
   - Family vs coach: both POST to `/tournaments/:id/families` (app.js 631 and 724). Lost family "Bennett", then "Add a coach: Mike" gives a row called Mike with role Coach and kind still "family", and Bennett is gone. Toast: "Added". The reverse (lost coach, then a family) renames the staff row to Bennett with a blank role and it stays staff, so its costs are no longer shared. Both are silent data corruption.
   - Person: lost add of Rosa, then a different person typed before the reload result arrives. If the reload itself failed, the Rosa check is skipped, and Ben's add renames Rosa to Ben.

2. The 409 is a dead end that produces the duplicate the design exists to stop. Touched row: `save` returns 409 "have a look at the list". `failed` is set, the name is restored into the box (app.js ~826-833), and the key was already dropped by `api()`. The next tap gets a new key and adds a second Ava. Same shape for families. The trip version of the 409 is also wrong for finalized or trashed trips, which fail the `status='open'` and `deleted_at` guards but get the "changed since" message (src/index.ts ~369-372).

3. Keys are dropped on any HTTP answer, including gateway errors. `if (adds) forgetAddKey(path)` runs right after fetch resolves. A 502/504/524 from the edge can come after the Worker committed. The next tap then duplicates. For expenses, `keepPending` only runs when `e.status == null`, so a gateway error is not remembered at all; the draft in sessionStorage dies with the tab.

4. A stalled body is not covered. The abort timer is cleared in `finally` once headers arrive (app.js ~90-96), and `await res.json()` has no timeout. Headers arrive, the body stalls: for people the key is already gone; for expenses `saveExpense` never reaches `catch`, so it sits on "Saving…" forever and nothing is remembered.

5. The add button can lock. The person handler sets `busy` and disables the button (app.js 816, 819). If the reload after a lost reply fails, `renderFamily` never runs, so the button stays disabled until the screen is left. The retry the design depends on is blocked.

**Other gaps**

6. The 10-minute TTL counts from the first attempt, not the last (`addKeyFor` never refreshes `at`). A retry after 10 minutes is a new key and a duplicate. Add keys live in sessionStorage, so closing the tab loses them, while pending expenses live in localStorage and survive. The two adds are not treated the same way.
7. Same-key races: people, family and trip inserts have no `ON CONFLICT`, so a second concurrent request with the same key gets a unique-violation 500 (src/index.ts 554, 657, 376). The client then drops the key and the next tap duplicates. The expense insert does handle this (`ON CONFLICT DO NOTHING`).
8. Deleted expenses are resurrected. Expense delete is a hard delete (src/index.ts 774), with no tombstone. An expense that landed, was then deleted by another phone, and then re-saved from the pending draft is recreated, and the phone was told it "may not have saved". Telling "never landed" from "landed and was deleted" needs a tombstone or the server remembering keys.
9. The pending expense is one slot for the whole browser (app.js 1102-1105). A failed save in another trip or another expense overwrites it. Also, app.js 876 drops the pending as soon as it is put back into the form. If the parent closes the tab before re-saving, it is gone, which breaks "remembered across closing the page".
10. Spec mismatch on "touched": the server checks only name and fencer flag for people, and name, role and notes for families. Day changes made on another phone do not block a correction. Harmless in practice, but not what was promised. Also, a fencer-to-non-fencer correction leaves `fencing_days` non-empty, unlike the PATCH path (src/index.ts 689). Probably harmless; check split.js line 46 filters by `is_fencer`.
11. Outside the spec: a lost reply on an expense edit (PATCH) followed by a corrected retry gets 409 "someone has changed this expense", which blames the parent's own edit. The rule only covers an identical retry.

**Does it break today's behaviour?** I found no regression on the ordinary path. Old clients still work with the new server (the key is ignored), and the schema change is nullable columns plus partial unique indexes. Retries now return 200 instead of 201, which the client ignores.

**Complexity.** The most complicated and most dangerous part is the corrected-retry machinery: three columns, an "untouched" comparison that compares stored columns to the signature, a 409 with no recovery, and three different notions of "touched" (`client_sig`, `rev`, and name-only). It buys only typo correction after a lost reply, and it is where the rename, merge and dead-end bugs come from. A simpler rule: a retry with identical details returns the existing row; a retry with different details returns it unchanged and says "Av was added after all; it's listed as Av, fix the name in the list." That removes items 1-2 and most of 10, and leaves the three columns and the `untouched` logic unnecessary. If the typo fix must stay, at minimum scope the key per kind (or per form) and drop it only on success or an explicit "different person" action.

**Holds up:** identical retry after a lost reply; double-tap guard; expense re-save with the same key; "did save" on the trip screen when the expense is still there.
