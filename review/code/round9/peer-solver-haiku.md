Short answer: the cause is that the retry key lives in the wrong place. The server already has retry keys (`client_key`, migrations 0009 and 0010) for expenses, people, families and trips, so exact retries are safe. The gaps are in how the phone makes and keeps those keys. I read the code and changed nothing.

What the code does now (src/index.ts, public/app.js):
- People and families: the phone keeps the key in an in-memory Map (`addKeys`, app.js:57 and 74–85), keyed on the path plus the JSON body. That is why both of your cases fail. A typo fix changes the body, so the key changes and the server inserts a second row. A page reload empties the Map, so the key is gone. The server only dedupes when the body is byte-identical and the page was never reloaded.
- Expenses: the key is a UUID made when the form opens (app.js:861) and stored in the draft. Reloads are covered, because the draft is kept in sessionStorage (app.js:1080–1083). But when the parent gives up on that form and enters the expense again, the new form gets a new UUID. The server has no way to connect the two, so the expense is in twice and split twice. That is case 1, and it is not caught by the existing retry key.
- Server-side, a same-key expense retry with corrected content is applied as an update if nobody else has edited it (rev = 0), and is refused otherwise. That is sensible, and it is what a people/family fix would also need.

Approach A: make the key belong to the intent, not the request or the form (recommended)
- Create one key when the parent opens the add sheet or new-expense form. Keep it in sessionStorage with the draft (people and families need this too, not only expenses). Send it on every attempt, including after an edit, a reload, or a "start over" that follows an unknown reply.
- On a same-key retry with changed content, the server updates the record it already made, using the same rev guard the expense path uses. So "Av" becomes "Ava" in place rather than becoming a second row.
- For case 1, the phone should not wait for the parent to start over. After an unknown-outcome error, the app keeps the pending key in localStorage with a short expiry. The next time the trip opens, it asks the server whether that key exists (this needs a small new read-by-key endpoint) and shows "Lunch, $20, added just before the connection dropped. Keep it / Remove it / Edit it." That is one tap, and it avoids the parent re-entering anything.
- Cost to parents: nothing when it works. The sheet looks the same and no extra question appears in the normal case. Only a dropped reply costs them a banner.
- What it could get wrong: (1) a key lost with the tab or browser (sessionStorage is per tab, and a new phone has none) still duplicates, so it needs the backstop below. (2) If someone else has edited the person or expense since, the update must refuse, and the parent needs a clear "someone changed this; open it from the list" message. The current 409 text is a model for that. (3) A parent who deliberately adds a second, identical expense after seeing the first in the list gets a new key, so that is fine. But a "pending" banner that lingers can be wrongly tapped as "Keep it" for something the parent meant to be new, so it should expire quickly and show the item's amount and time.

Approach B: a server-side near-duplicate check (backstop, not the main fix)
- Before inserting a person, family or expense, look for a row in the same family or trip, with a similar name (or same description, payer, amount and date for expenses) and created in the last few minutes. If one exists, return it with a question: "Ava was just added by Sam (2 min ago). Use that one, or add a new one?"
- Cost: a question in a rare case, and only when the match is close. It also needs the creator name shown, so it reads as "someone already did this" rather than "the app is confused".
- What it could get wrong: this is the one most likely to fail the "two parents add similar things" case. Twins or cousins in one family, a real second "Ben", or two identical $20 lunches for two kids on the same day all look like duplicates. Fuzzy matching also misses real typos ("Avaa" vs "Ava" is fine, but "Av" vs "Eva" is a different name), and a match that is too loose creates extra taps. If built, it should only prompt, never block, and the prompt should always offer "add a new one".

My recommendation: build A. It is deterministic, costs parents nothing in the normal case, and only needs the key to be carried forward, not new guessing logic. Add B later, and only if the logs show duplicates still getting through after A, because it is the part that will annoy the most parents when it is wrong.
