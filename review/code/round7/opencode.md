### [MEDIUM] A stale PATCH can restore a deleted receipt after another phone replaced it
File: src/index.ts:655-660. Scenario: expense E has receipt K0. Phone A opens E (reads `old` with K0). Phone B uploads K1 and saves: its PATCH reads K0, the HEAD check passes for K1, the row is updated to K1, and `dropReceipt(K0)` deletes K0. Phone A then saves with the unchanged K0 before its own UPDATE runs. Because `e.receipt_key` equals the stale `old.receipt_key` (K0), the new HEAD check is skipped, and the UPDATE, guarded only by `id`, `created_at` and OPEN, writes K0 back. Wrong outcome: E now points at a file B deleted; B's K1 is unreferenced and later purged, while both phones report success. The same window lets a stale save that removes the receipt silently discard B's replacement. Suggested fix: include the seen receipt key in the write, e.g. `AND receipt_key IS ?` bound to `old.receipt_key`, and fail with 409 on 0 changes; only drop the old file after a winning update.

### [LOW] POST does not check that a supplied receipt still exists
File: src/index.ts:635-638. Scenario: on the practice trip, a parent uploads a receipt for a new expense and leaves the form open for over an hour. Another parent resets the practice trip; `resetSandbox` then `dropOrphanReceipts` deletes the unreferenced upload. The first parent saves, and POST (unlike PATCH) never calls `RECEIPTS.head`, so the expense is inserted with the dead key. Wrong outcome: the saved expense shows a missing receipt and the upload is gone. Suggested fix: apply the same HEAD check used by PATCH before the POST insert.
