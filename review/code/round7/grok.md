### [MEDIUM] Typing a new person's name loses the cursor to another field, which then saves those letters

File: `public/app.js:724`. Scenario: Tap "Use the family's days again" or "Different days?" and, while that save is still running, type a new person's name in "Add a person". `#newname` is no longer treated as the field being typed in, so line 730 applies that save's `focusAfter` (`[data-pname="…"]` or `[data-own="…"]`) instead of staying in the add box. The letters already typed are put back in the add box, but the cursor is moved. Wrong outcome: On "Use the family's days again", the next letters go into the existing person's name and are saved when that field blurs, so that person is renamed with the new person's text. On "Different days?", the keyboard closes and those letters are dropped, and Add submits a shortened name. Suggested fix: Count `#newname` as typing for the focus choice, the same as the other text fields, and still do not send a save for it.

### [MEDIUM] A slow refresh paints over a newer reload of the same trip

File: `public/app.js:230`. Scenario: Tick a payment, save trip details, or add a family, so `refresh()` is fetching. Switch to another app and come back before that fetch returns. Coming back runs `route()` on the same address, which loads the trip again. `refresh()` no longer notices that load. Whichever response returns last calls `renderTrip`. Wrong outcome: If the older response returns last, the screen goes back to balances, payment ticks, or trip dates from before the newer load. Text typed into Trip details after the resume is cleared. Leaving the trip and opening it again shows the real figures. Suggested fix: Let a same-address resume reload paint, but ignore a `refresh` response once a later load has already been applied.
